# Build and understand the project in IntelliJ

This guide assumes you know classes, loops, and collections. Everything is Java; ML algorithms come from the Smile library. The numbered source companion explains the application's individual source lines. The mathematics and engineering choices are explained here.

## 1. Understand the business problem before writing code

B2B means business-to-business: one company sells a product to another company. Our example product is a pack of 100 M8 bolts, product ID BOLT-M8-100. One model handles one product.

Selling at a higher price increases margin per pack, but it may reduce the number of packs bought. A useful recommendation needs both effects. We predict demand, then compare prices.

Let p be candidate price, c unit variable cost, q predicted daily demand, and s available stock:

```text
sellable units = min(max(0, q), s)
estimated gross contribution = (p - c) * sellable units
```

Example: price INR 120, cost INR 80, expected sales 50 packs, stock 80. Expected contribution is (120 - 80) * 50 = INR 2000. This excludes fixed costs and other expenses. It is not net profit.

The actual simulation recommendation differs from this introductory arithmetic because its model predicts demand for a different buyer/context and compares many prices.

## 2. Create or open the project

You can either open the delivered project or recreate it file by file using the delivered sources.

To recreate it:

1. In IntelliJ choose New Project → Java.
2. Name the folder **b2b-pricing-java** and choose **Maven** as the build system.
3. Select an installed JDK 17 or newer.
4. Use group ID **com.mitanshu** and artifact ID **b2b-pricing-java**.
5. Replace the generated pom.xml with the supplied file.
6. In src/main/java, create package **com.mitanshu.pricing**.
7. Create each Java class using the exact supplied filename and package declaration.
8. Copy data/, docs/, and src/main/resources/ from the supplied project.
9. Reload/sync Maven after replacing pom.xml.

To open the complete project: File → Open → select pom.xml → Open as Project.

File → Project Structure → Project SDK chooses the JDK used by this project. The Maven setting maven.compiler.release=17 means the generated bytecode and available language/API features target Java 17 even if your computer uses a newer JDK.

If IntelliJ opens a single Java file rather than the project, close it and open pom.xml. The IDE should recognise src/main/java as source code and src/test/java as tests.

## 4. First runnable lesson: SetupCheck

Open SetupCheck.java, then use the green run arrow next to main. Expected output includes:

```text
B2B Dynamic Pricing Optimization Engine
Java version: <your installed JDK version>
Estimated gross contribution: INR 2000.0
Setup check passed.
```

- **package** gives the class its qualified name, com.mitanshu.pricing.SetupCheck.
- **public class** declares a class other code can access.
- **public static void main(String[] args)** is Java's conventional entry point. Public makes it accessible, static removes the need to instantiate the class, void means it returns no value, and args receives command arguments.
- **String** stores text; **double** stores decimal numbers; **int** stores a whole-number count.
- Parentheses calculate sellingPrice - unitCost first. Multiplication then applies this margin to quantity.
- **System.out.println** writes a line to the console.
- **System.getProperty("java.version")** reads the JDK's version property.
- A semicolon ends a statement; braces group statements inside the method/class.

Try changing quantity from 50 to 60. The result should become INR 2400.0. Change sellingPrice to 75 with quantity 50 and cost 80. The arithmetic becomes INR -250.0. The full pricing engine later handles such cases by withholding a recommendation when every allowed price has nonpositive contribution.

## 5. Understand the synthetic dataset

| Column | Example | Meaning |
| --- | --- | --- |
| date | 2024-01-01 | Daily observation date |
| product_id | BOLT-M8-100 | The single product being modelled |
| price | 120.00 | Offered price in INR per pack |
| competitor_price | 125.00 | Known external competitor reference price per comparable pack |
| customer_segment | 1 | 0 = smaller buyer segment; 1 = larger buyer segment |
| season_index | 1.00 | Known market/season indicator; 1 is neutral |
| unit_cost | 80.00 | Variable cost per pack; used in the contribution calculation |
| quantity | 50.00 | Observed daily demand/sales quantity, the prediction target |

The simulator creates one observation per date for one SKU. It is not a multi-line invoice table. All historical quantities are assumed to be observed without stockout censoring.

The four ML features, in fixed order, are price, competitor price, customer segment, and season index. Quantity is the target. Product ID is constant; date defines the split; cost affects contribution but is not a feature in this particular simulator.

The hidden simulator expectation is:

```text
q = max(0,
        115 + 25 * segment + 30 * (seasonIndex - 1)
        - 1.4 * (price - 100)
        + 0.45 * (competitorPrice - 120))
```

It adds Gaussian observation noise with standard deviation 3 packs and rounds actual observations to whole packs. Prices, segments, competitor prices and season indices are randomised using a seeded generator.

The ML code receives only CSV observations, not this formula. The formula is available for explaining the simulator, not for training directly on a known answer.

**Seed 42** makes the dataset reproducible. Calling generate with an existing path fails instead of destroying an existing dataset. To try a new dataset, choose a new filename.

## 6. Data validation and cleaning

Transaction is a Java record: its components become private final fields, accessor methods, and equality methods. The compact constructor runs validation whenever a record is created, including when the CSV loader creates it.

Validation checks finite numbers, positive prices/costs, nonnegative quantities, supported segment values, and a bounded season index. NaN and Infinity are rejected because they can break numerical calculations without behaving like ordinary numbers.

CsvData uses named CSV columns but deliberately requires the documented complete header order. It trims field whitespace, rejects missing values and inconsistent rows, rejects duplicate dates, requires one product, and sorts dates.

The learning edition fails fast rather than guessing replacement values or silently discarding questionable data. Those choices must be made based on a real dataset's meaning. An imputation pipeline is not implemented here.

try-with-resources closes the file Reader and CSVParser even if an error occurs. A record number in the error helps find the offending CSV observation; for a normal one-line record, the physical file line is normally record number + 1 because of the header.

## 7. Training, validation, and test separation

The sorted 720 rows are split into:

- **432 training rows (60%):** fit model parameters and scaling statistics.
- **144 validation rows (20%):** select among the three fixed candidate models.
- **144 test rows (20%):** report final error on later, unseen observations.

Chronological splitting simulates predicting future observations. A random split could place future observations in the training set.

The models remain fitted on the original training partition. We do not refit using validation data after selection in this edition. Thus the model used for recommendations is exactly the model whose test metrics were reported.

Hyperparameters are fixed in source before test evaluation. Test errors are printed for comparison, but the selection code uses validation RMSE only. Repeatedly editing parameters after viewing test scores would make the test set a tuning set and would require a new untouched holdout.

## 8. The three models

### Mean-demand baseline

It always predicts the average training quantity. It ignores price/context. It provides a reference: complex code is not automatically better than a simple average.

If this baseline wins validation, the pricing engine withholds the price-sensitive recommendation. A constant-demand prediction cannot establish a learned price-demand relationship.

### Random Forest regression

A regression tree repeatedly partitions observations using rules such as price <= threshold. A leaf predicts a mean quantity for the observations in that leaf. A forest averages the predictions of many trees.

Our forest uses 80 trees, bootstrap samples, 3 candidate features per split, maximum depth 12, maximum 100 leaf nodes, and minimum node size 5. Different seeded samples produce different trees; averaging reduces dependence on any one tree.

The target is specified by Formula.lhs("quantity"). The DataFrame includes the four predictors and target; Smile excludes the target from predictors through the formula. During prediction we include an unused zero target slot to preserve the schema; that slot is not used as a feature.

We use the supplied library implementation. We have not added cross-validation or feature-importance plots in this edition.

### Support Vector Regression

SVM is commonly discussed for classification. Because our output is a continuous number of packs, we use its regression form, **SVR**.

SVR tries to fit a function while allowing a small epsilon band around predictions. C controls the penalty for errors outside this band. A Gaussian kernel lets the function represent nonlinear relationships without explicitly writing all nonlinear features.

We use Gaussian sigma 1.5, epsilon 0.05 on the normalised target, C=10, and solver tolerance 0.001. These are demonstration settings, not a claim of universally optimal values.

Features have different units: price is around 100, while seasonIndex is around 1. Standardizer calculates z=(x-trainingMean)/trainingStandardDeviation. The target is normalised using its training mean/deviation and converted back to pack units after prediction.

Only training rows determine these statistics. Constant feature columns use deviation 1 to avoid division by zero. Validation/test values are transformed with already-fitted statistics, never used to recompute them.

## 9. Measure model errors

For each observation, error = predicted quantity - actual quantity.

```text
MAE  = average(abs(error))
RMSE = sqrt(average(error * error))
```

Both are measured in packs. RMSE penalises large errors more strongly than MAE. Lower is better on the same test data, but predictive error alone does not prove good pricing decisions.

The code clips negative predictions to zero consistently for evaluation and pricing. It refuses non-finite predictions. It does not provide calibrated prediction intervals.

## 10. Compare candidate prices

Request contains current price, cost, minimum/maximum price, step, stock, competitor reference price, buyer segment, and season index.

Example: current 120, cost 80, allowed prices 100 through 150, step 1, stock 80, competitor 125, segment 1, season 1.0.

For each of the 51 candidate prices:

1. Create the four-feature vector with the candidate price and unchanged context.
2. Ask the selected demand model for predicted units.
3. Clip a negative result to zero, and cap sellable units at stock.
4. Compute gross contribution using the candidate price and cost.
5. Retain the candidate with the greatest positive contribution.

The maximum bound is included even when step does not land on it. Exact contribution ties retain the lower price because prices are visited in increasing order.

Currency/grid steps use exact integer cents for iteration. BigDecimal rejects money with more than two decimal places; it does not silently round the user's input.

Prediction, quantities and estimated contribution still use double. This is suitable for statistical expectations, not an accounting ledger implementation.

Current price is a comparison point, not automatically added to a grid that excludes it. If the best allowed candidate estimates less contribution than current price, the output flags it.

## 11. Outcome catalogue

No project can enumerate every imaginable real-world outcome. This edition specifies and tests its supported input domain and main failure classes.

| Situation | Behaviour |
| --- | --- |
| Valid inputs and positive contribution | RECOMMENDED; show candidate price and estimates |
| Stock is zero | NO_STOCK; no recommended price |
| All candidates have nonpositive contribution or zero predicted demand | NO_POSITIVE_CONTRIBUTION |
| Mean baseline wins validation | BASELINE_SELECTED; price-sensitive recommendation withheld |
| Negative model output | Clip demand to zero and add an output note |
| Non-finite or extremely large model output | Fail with a model error |
| Minimum exceeds maximum | Reject input |
| Zero/negative step | Reject input |
| More than two decimals in money | Reject input |
| Negative/excessive stock | Reject input |
| Unsupported segment/season | Reject input |
| Price/context outside observed training feature range | Reject extrapolation |
| Too many candidate prices | Reject and ask for a larger step |
| Minimum equals maximum | Evaluate one candidate |
| Step does not reach maximum exactly | Also evaluate maximum |
| Candidate contribution ties | Prefer lower price |
| Missing file, wrong header, missing value, bad number, broken CSV | Fail with an explanatory error |
| Duplicate daily observation or mixed product IDs | Reject the file |
| Fewer than 200 observations or constant training quantities | Reject training |
| Existing synthetic output file | Preserve it and fail generation |
| Desktop unavailable | Use console commands; gui reports unavailable display |
| Invalid text in desktop fields | Show error; keep application usable |
| Report folder cannot be written | Report the I/O failure |

Feature-range checks are marginal checks. They cannot prove that every combination was well represented, nor that a changing future market will behave like this simulator.

## 12. Console and desktop application flow

No arguments selects demo. demo loads the supplied data (or generates it only if the requested demo path does not exist), trains, evaluates, recommends, and exports.

Main catches errors at the application boundary, prints ERROR, and exits with code 1. This makes automated runs detect failures.

DesktopApp creates Swing components on the Event Dispatch Thread. Training and recommendation/export run in SwingWorker background tasks so the form does not freeze while doing that work. done() returns to the UI thread to display results and re-enable the button.

Data/model logic is separate from presentation. The console and desktop both call the same TrainingPipeline and PricingEngine. They do not maintain two conflicting implementations.

There is no REST API/server in this version; the desktop interface is implemented. A web/API version can be added after the core is understood.

Run Maven test or use IntelliJ to run the test package. Tests use small controlled fixtures for arithmetic and validation, plus real Smile models for integration.

The key checks include a known analytical price-grid optimum, inventory caps, exact-cent grids, ties, malformed data, reproducible generation, chronological partitions, scaler behaviour, validation-based selection, report exports, desktop background completion, and invalid desktop text.

## 14. Debug with IntelliJ

Set a breakpoint by clicking the gutter beside an executable line, then choose Debug instead of Run.

Suggested breakpoints:

- After CSV rows are sorted: inspect rows.size(), row dates, and product IDs.
- After split boundaries: inspect trainingEnd and validationEnd.
- After validation metrics: inspect the three RMSE values and best index.
- Inside candidate evaluation: inspect price, features, demand, units, and contribution.
- Before final result: inspect best versus current.

Use Step Over for your application statements. Step Into enters a called method; stepping into Smile immediately can be overwhelming, so first follow your wrapper methods.

Remember that a record accessor is price(), not getPrice(), and that array indices start at zero.

## 16. Explain the project in an interview

A truthful explanation is: “I built a Java learning project on reproducible synthetic B2B data. It validates daily observations, compares a baseline with Random Forest and SVR using chronological partitions, and chooses a demand model using validation RMSE. A separate pricing service evaluates a constrained price grid using cost and inventory. I tested failure cases and provided console/desktop interfaces and CSV diagnostics.”

Be able to explain why historical-price prediction is not price optimisation, why quantity is the target, why preprocessing must not use test data, why synthetic results are not real profit improvements, and why real pricing needs causal/experimental evidence.
